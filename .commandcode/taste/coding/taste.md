# Coding Preferences

- Works in Laravel with Livewire, Alpine.js, and Vue.js; expects the assistant to be competent in that stack. Confidence: 0.9
- Uses Livewire class + separate Blade view; never single-file Livewire components. Confidence: 0.95
- Alpine.js is only for local UI state; no custom JavaScript for CRUD operations. Confidence: 0.9
- Follows the existing admin/dashboard UI style exactly (spacing, cards, typography, buttons, borders, modals, responsive behavior); do not redesign. Confidence: 0.9
- Do not install new UI libraries. Confidence: 0.85
- Prefers additive migrations; never modifies previously working auth/role migrations. Confidence: 0.9
- Avoids over-engineering: no extra packages, abstractions, repositories, services, or components unless the scope requires them. Confidence: 0.9
- Use backed enums (e.g. status enums) when consistent with existing project style. Confidence: 0.7
- Prioritizes data safety over features — e.g. avoid hard-deleting records that have relations rather than implementing full delete. Confidence: 0.7
- Prefers reusable UI built as classless (anonymous) Blade components under `resources/views/components/...` (e.g. `admin/ui/*`, `admin/form/*`) rather than class-based components. Confidence: 0.75
- Expects Blade components to expose flexible props, keep their slots, and forward extra attributes via `$attributes->merge()` so `wire:model`/`wire:click`, `data-testid`, `aria-*`, and CSS classes still pass through; must stay compatible with Livewire and Alpine. Confidence: 0.75
- Wants business/domain logic kept out of Blade views and Livewire classes — put it in dedicated service classes (e.g. `app/Services/*`) that controllers/components delegate to. Confidence: 0.8
- State-changing operations (e.g. ticket check-in) must be concurrency-safe: wrap them in database transactions and guard against double-processing/race conditions (e.g. `lockForUpdate`). Confidence: 0.8
- Values a clean, extensible Laravel structure with no duplicated logic across layers. Confidence: 0.7
- When given an existing design with its own plain CSS, preserve that CSS as-is and do not convert it to Tailwind (or introduce a new frontend framework). Confidence: 0.7
- Splits pages into small, focused Blade components rather than one large Blade file. Confidence: 0.65
- For statistics/dashboards, requires efficient DB access: use SQL aggregate/`GROUP BY` queries, never load full tables into memory, eager-load only when needed, and do not add caching unless asked. Confidence: 0.75
- Avoids adding realtime/websocket features, chart libraries, APIs, or export functionality unless explicitly requested; prefers server-rendered aggregate data. Confidence: 0.7
- Treats the browser-native `BarcodeDetector` as unreliable for camera QR decoding and prefers the `@zxing/browser` (ZXing) reader instead for camera-based registration flows; keep the established hardware-scanner approach — USB/Bluetooth 2D scanners as keyboard input with Enter submitting — with no custom Bluetooth/device integrations. Confidence: 0.75
- Prefers scanner/device logic encapsulated in a reusable, Livewire-agnostic Alpine component (e.g. registered via `Alpine.data('qrCameraScanner', ...)`) that owns start/stop/decode/permission-error handling and emits its result via events, rather than embedding scanner logic directly in Blade. Confidence: 0.7
- Prefers dedicated routed pages (e.g. `admin.tickets.create`) over modals for structured create/registration flows that involve multiple inputs or a scanner step. Confidence: 0.6
- Wants database seeders to be idempotent/re-runnable — key on unique columns with `firstOrCreate`/`firstOrNew` so `php artisan db:seed` can run repeatedly without creating duplicates. Confidence: 0.65
- Wants seed data that populates every domain state so all screens/dashboards have content (e.g. events across active/completed/draft, tickets both checked-in and not, check-in logs covering success/already-checked-in/invalid) rather than a minimal sample. Confidence: 0.6
- Wants action buttons to show visible loading feedback while their request is in flight — a spinner plus disabling the button to prevent double submits — applied consistently across the app (e.g. via the shared Blade button component) rather than per-button one-offs; loading should be scoped to the button's own action so unrelated buttons don't spin. Confidence: 0.7
- Per-row action buttons (edit/delete/activate/toggle on each table row) must pass the row id into `wire:target` (e.g. `wire:click="edit(1)"` with `wire:target="edit(1)"`) — Livewire's auto-derived target keeps only the method name and drops arguments, so without an explicit per-row target one click lights up every row's button. Confidence: 0.65
- Avoids Livewire's delayed loading bindings (e.g. `wire:loading.class.delay`) for button spinners — local requests finish before the ~200ms delay, so the loading class never gets applied; the loading state must be bound immediately (`wire:loading.class`) even if that makes it flash on very fast actions. Confidence: 0.6
- For camera/scan capture flows, expects the capture session to stay active after a successful read (no stop/release on success — release only on explicit user action, component destroy, or error) so the operator can scan repeatedly without re-activating, plus explicit duplicate-scan protection (a ~1-2s debounce/lock and same-value suppression) so one QR isn't emitted multiple times per cycle. Confidence: 0.6
- Prefers extending existing models/tables over introducing new ones — e.g. keep scanner accounts in the existing `users` table using the existing roles, adding only a simple boolean `is_active` flag, rather than creating a dedicated table or introducing a new permission system. Confidence: 0.65
- Authorization-sensitive fields must never be driven by form input: values like `role` are fixed server-side (e.g. always `UserRole::Scanner`) and the form exposes no way to change them, so a screen can't be used to escalate privileges. Confidence: 0.7
- Enforces access/business rules by extending the existing middleware (e.g. `EnsureUserHasRole`) rather than creating new middleware, policies, or auth event listeners; explicitly forbids touching the authentication core (Fortify, auth pipeline, login controller). Confidence: 0.75
- When gating a route, reuses the response convention the existing middleware already uses (e.g. `abort(403)`) instead of introducing new redirect-to-login or flash-message behavior. Confidence: 0.6
- Expects model factories to explicitly declare columns that carry a DB default (e.g. boolean flags like `'is_active' => true`) so the in-memory Eloquent instance matches the persisted row — otherwise the `boolean` cast turns an unloaded `null` into `false` and tests using that instance (e.g. `actingAs`) break. Confidence: 0.6
- Reuses the framework's existing routes/flows instead of building a parallel one — e.g. logout via the existing Laravel/Fortify `logout` route in a `POST` form with `@csrf`, no custom logout flow. Confidence: 0.65
- User/identity context shown in the UI (operator name, role, initials) must be derived from the authenticated user and passed down as data, never left to a hardcoded component prop default — a default that matches the common case (e.g. role `'Scanner'`) silently mislabels other roles until a test catches it. Confidence: 0.6
- When a precondition for the page's action is missing (e.g. no active event), render an explicit warning/empty state and omit the action UI entirely (no scan panels/buttons) rather than letting the action become an error downstream. Confidence: 0.55
